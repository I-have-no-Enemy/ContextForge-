# สคริปต์พูดประกอบสไลด์ ContextForge (หน้า 1-20)

ใช้คู่กับสไลด์ Canva หน้า 1-20 (ชุด template มืด) ส่วนเดโมสดใช้ `docs/DEMO.md` ข้อ 5 เวลารวมฝั่งสไลด์ประมาณ 11-12 นาที ไม่รวมเดโม

ไม่ต้องท่องคำต่อคำ จำประโยคแรกของแต่ละหน้าไว้ก็พอ ที่เหลือพูดตามภาพบนจอ

ระบบจริง (docs/API.md ข้อ 22) ให้ Public Generate Config ได้โดยไม่ต้อง Login ถ้า Login อยู่ Config จะถูกบันทึกผูกกับบัญชี สไลด์ต้องเขียนตามนี้ สิ่งที่ต้องแก้ใน Canva:

- หน้า 5 กล่อง Public: "ดูรายการ ค้นหา และ Generate Config ได้ทันที ไม่ต้อง Login"
- หน้า 5 กล่อง Developer: "Login เพื่อส่ง Server / Skill เข้าคิวรีวิว และบันทึก Config ไว้ดูย้อนหลัง"
- หน้า 11 เส้นทางที่สอง: "เลือก Tool ที่ผ่านการตรวจ → เลือก Client → Generate ได้ไฟล์ Config (Login แล้ว Config ถูกบันทึกในบัญชี)" และกล่อง "Developer Login" ที่อยู่หน้า Generate เปลี่ยนเป็น "Login (ไม่บังคับ)"
- หน้า 18 ตัวเลข Skill: "อนุมัติแล้ว 138" (ของเดิม 144 / 135 เป็นตัวเลขเก่า)

## หน้า 1 ปก (20 วินาที)

> สวัสดีครับอาจารย์ วันนี้ผมจะนำเสนอโปรเจกต์ ContextForge หรือชื่อในข้อเสนอคือ AI & MCP Skill List เป็นเว็บกลางสำหรับรวม MCP Server กับ AI Skill ที่ผ่านการตรวจแล้ว และช่วยสร้างไฟล์ Config ให้ AI client ครับ

## หน้า 2 สารบัญ (20 วินาที)

> ลำดับการนำเสนอมี 7 ส่วนครับ เริ่มจากที่มาและแนวคิด, จุดประสงค์กับ Flow ของแต่ละ role, Tech Stack, Database กับ ERD, Endpoint หลัก, สิ่งที่ทำเพิ่มกับผลตรวจ แล้วปิดด้วยงานที่ยังไม่ได้ทำครับ

## หน้า 3 ที่มาของเรื่อง (60 วินาที)

> ตอนนี้คนที่ใช้ AI Agent อย่าง Claude Desktop, Cursor หรือ Cline เริ่มติดตั้ง MCP Server เพิ่มกันเยอะขึ้น แต่การติดตั้งมีปัญหาอยู่ 2 เรื่องครับ
>
> เรื่องแรกคือยุ่งยาก ต้องไปหา JSON Config จากหลายเว็บมาก๊อปวางเอง และแต่ละ client เขียน config ไม่เหมือนกัน
>
> เรื่องที่สองคือความปลอดภัย MCP Server บางตัวอ่านไฟล์ ลบข้อมูล หรือต่อเน็ตได้ โดยที่ผู้ใช้ไม่รู้ เพราะไม่มีที่ไหนบอกระดับความเสี่ยงไว้
>
> ผมเลยทำเว็บนี้ขึ้นมาให้เป็นที่เดียวที่รวมเครื่องมือพวกนี้ ตรวจก่อนเผยแพร่ แล้วประกอบไฟล์ Config ให้ใช้ได้ทันทีครับ

## หน้า 4 แนวคิดและความสำคัญ (40 วินาที)

> แนวคิดหลักคือทำเป็น Registry กลางครับ ทุก Tool ต้องมี Input Schema ที่ถูกต้อง ระบบจัดระดับความเสี่ยงไว้ 4 ระดับคือ read_only, network, filesystem และ destructive แล้ว Admin ต้องอนุมัติก่อนคนทั่วไปถึงจะเห็น
>
> พอผ่านแล้ว Developer เลือก client ที่ใช้ ระบบก็สร้าง Config ให้ตามรูปแบบของ client นั้น ช่วยได้ทั้งเรื่องความปลอดภัยและเวลาที่ใช้ติดตั้งครับ

## หน้า 5 จุดประสงค์ (40 วินาที)

> ผู้ใช้แบ่งเป็น 2 กลุ่มหลักครับ
>
> กลุ่มแรก Public เข้าเว็บมาดูรายการเครื่องมือได้เลยโดยไม่ต้อง Login เลือก Tool ที่ผ่านการรับรองแล้ว เลือก client ว่าจะใช้กับ Claude Desktop, Cursor หรือ Cline กด Generate Config แล้วก๊อปไฟล์ไปวางในโปรแกรมของตัวเองได้ทันที
>
> กลุ่มที่สอง Developer Login เพื่อส่ง Server หรือ Skill ของตัวเองเข้าคิวรีวิว และ Config ที่ Generate ตอน Login อยู่จะถูกบันทึกไว้ในบัญชี เปิดดูย้อนหลังได้ครับ

## หน้า 6 Flow การใช้งานตาม Role (30 วินาที)

> ในระบบจริงมี 3 role ครับ คือ Public, Developer และ Admin แต่ละ role ทำอะไรได้ไม่เท่ากัน ผมแยกไดอะแกรมไว้ 3 หน้าถัดไป จะไล่ให้ดูทีละ role ครับ

## หน้า 7 Flow ของ Public (30 วินาที)

> Public ดูรายการ ค้นหา และเปิดหน้ารายละเอียดของ Server หรือ Skill ที่อนุมัติแล้วได้ และกด Generate Config แบบไม่บันทึกได้ด้วย แต่ถ้าจะส่ง Server หรือ Skill เข้าระบบต้องสมัครสมาชิกก่อน ฝั่ง API ถ้าไม่มี token ระบบตอบ 401 ครับ

## หน้า 8 Flow ของ Developer (40 วินาที)

> Developer ส่ง Server หรือ Skill ของตัวเองเข้ามาได้ ของที่ส่งจะเข้าคิวรีวิวก่อนเสมอ ยังไม่เผยแพร่ทันที
>
> อีกงานหนึ่งคือสร้าง Config เลือก Tool แล้วเลือก client ได้ไฟล์ JSON ออกไป ต่างจาก Public ตรงที่ Config ของ Developer ถูกผูกกับบัญชีและเปิดดูย้อนหลังได้ Developer แก้หรือลบได้เฉพาะของที่ตัวเองส่ง ถ้าไปแก้ของคนอื่นระบบตอบ 403 ครับ

## หน้า 9 Flow ของ Admin (40 วินาที)

> Admin ดูคิวรีวิว อ่านผลสแกน แล้วอนุมัติหรือปฏิเสธพร้อมใส่เหตุผล ถ้าของที่อนุมัติไปแล้วมีปัญหาทีหลัง Admin ถอดออกได้ทันที และทุกการตัดสินใจจะถูกบันทึกลงตาราง submission_reviews ครับ

## หน้า 10 Tech Stack (60 วินาที)

> Tech Stack ครับ
>
> Frontend ใช้ React 18 กับ TypeScript build ด้วย Vite 6 session เก็บใน HttpOnly cookie เพื่อไม่ให้ JavaScript ฝั่งหน้าเว็บอ่าน token ได้
>
> Backend ใช้ Express 4 กับ TypeScript แบ่งเป็น routes, controllers, services ตรวจ input ด้วย zod รหัสผ่าน hash ด้วย bcrypt cost 12 และมี rate limit ตอบ 429
>
> Database เป็น PostgreSQL 17 บน Supabase ใช้ Prisma 5 จัดการ migration มี 6 ตาราง
>
> API เป็น REST ใต้ /api/v1 มี 31 endpoint ทดสอบด้วย Vitest 197 เทสต์ และ Postman 55 request แล้ว deploy บน Vercel ครับ
>
> เส้นล่างคือทางเดินของ request: React เรียก API พร้อม cookie, Express ตรวจด้วย zod, ส่งต่อให้ Prisma แล้วลง PostgreSQL ครับ

## หน้า 11 Flow ภาพรวมฟีเจอร์ (60 วินาที)

> หน้านี้สรุป Flow ทั้งระบบครับ มี 2 เส้นทางที่ทำงานคู่กัน
>
> เส้นทางแรกคือ Admin ตรวจ Tool ใหม่ ประเมินความเสี่ยง แล้วตั้ง is_verified เป็น true
>
> เส้นทางที่สองคือผู้ใช้เลือก Tool ที่ผ่านแล้ว เลือก client กด Generate ได้ไฟล์ Config ตรงนี้ไม่บังคับ Login ถ้า Login อยู่ Config จะถูกบันทึกในบัญชี
>
> จุดที่อยากให้อาจารย์ดูคือเส้นประจาก Admin มาหาผู้ใช้ครับ ผู้ใช้จะเลือก Tool ไปสร้าง Config ได้ก็ต่อเมื่อ Admin ตรวจผ่านแล้ว ถ้าไม่มีขั้นนี้ เรื่องความปลอดภัยที่พูดมาทั้งหมดก็ไม่มีผลครับ

## หน้า 12 Database ที่เลือกใช้ (50 วินาที)

> ผมเลือก PostgreSQL ครับ เหตุผลคือ Input Schema ของแต่ละ Tool เป็น JSON ที่ซ้อนกันหลายชั้นและแต่ละตัวโครงสร้างไม่เหมือนกัน PostgreSQL มี JSONB เก็บได้ตรงๆ และใช้ GIN index ค้นข้างใน JSON ได้เร็ว
>
> แต่ระบบนี้ก็ต้องการ Foreign Key ที่เข้มงวดด้วย เพราะ Server, Tool, Config และ Review ผูกกันหมด เลยไม่เลือก MongoDB ที่ได้ JSON แต่เสีย relational integrity ไปครับ

## หน้า 13 ERD 6 ตาราง (60 วินาที)

> ฐานข้อมูลมี 6 ตารางครับ
>
> - users เก็บบัญชีกับ role
> - mcp_servers เก็บ MCP Server แต่ละตัว
> - tool_definitions เก็บ Tool ใน Server พร้อม input_schema กับ risk_level ถ้าลบ Server ระบบลบ Tool ตามแบบ Cascade
> - ai_skills เก็บ Skill
> - client_configs เก็บ Config ที่ Generate ไปแล้ว
> - submission_reviews เก็บผลการรีวิวของ Admin
>
> ทุกตารางที่มีคนส่งข้อมูลจะมี submitted_by ชี้ไปที่ users และ Server กับ Skill ใช้ soft delete คือมี is_deleted กับ deleted_at แทนการลบจริง เพื่อให้ Config ที่เคยสร้างไปแล้วยังอ้างถึงได้ครับ

## หน้า 14 Endpoints 1-11 (40 วินาที)

> Endpoint มีทั้งหมด 31 ตัว แบ่ง 5 กลุ่มครับ หน้านี้เริ่มจากข้อ 1 คือ /health ไว้เช็กว่า service ทำงาน ข้อ 2-5 เป็น Auth คือสมัคร Login ดูข้อมูลตัวเอง และ Logout
>
> ข้อ 6-11 เป็น MCP Server GET รายการกับรายละเอียดเปิดให้ Public ส่วน POST ต้อง Login ส่วน PATCH กับ DELETE ต้องเป็นเจ้าของหรือ Admin ข้อ 11 ลบแบบ soft delete ได้ 204 กลับมาครับ

## หน้า 15 Endpoints 12-21 (40 วินาที)

> ข้อ 12-14 เป็น Tool ใน Server ดู เพิ่ม และลบ Tool ได้ ข้อ 15-21 เป็น AI Skill ใช้หลักเดียวกับ Server ครับ อ่านได้ทุกคน สร้างต้อง Login แก้กับลบต้องเป็นเจ้าของ
>
> ที่ต่างคือข้อ 17 /skills/scan ให้ Developer สแกนเนื้อหา Skill ก่อนส่ง จะได้เห็นว่ามีอะไรติดธงบ้างครับ

## หน้า 16 Endpoints 22-31 (50 วินาที)

> ข้อ 22-24 เป็น Config Generator ข้อ 22 Generate ได้แม้ไม่ Login แต่ถ้า Login อยู่ Config จะผูกกับบัญชี แล้วดูย้อนหลังได้ที่ข้อ 23
>
> ข้อ 25-31 เป็นของ Admin ทั้งหมดครับ ดูสถิติ ดูคิว รีวิว ถอดถอนฉุกเฉิน ซิงก์และนำเข้าจาก GitHub และอนุมัติรายการนำเข้าที่สแกนไม่เจออะไรในครั้งเดียว ถ้า role ไม่ใช่ admin ได้ 403 ครับ เอกสารเต็มอยู่ใน docs/API.md

## หน้า 17 สิ่งที่ทำเพิ่มจากข้อเสนอเดิม (60 วินาที)

> จากข้อเสนอเดิม ผมทำเพิ่ม 6 เรื่องครับ
>
> 1. บัญชีผู้ใช้จริง รหัสผ่าน hash ด้วย bcrypt token อยู่ใน HttpOnly cookie และระบบรู้ว่าใครเป็นใครจาก token อย่างเดียว ไม่รับ id จาก body
> 2. สแกน Prompt Injection ในเนื้อหา Skill ก่อนเข้าคิว ถ้าเจอจะติดธงให้ Admin อ่านเอง
> 3. นำเข้าจาก GitHub ผ่าน api.github.com เท่านั้น ของที่นำเข้าก็ต้องเข้าคิวรีวิว ไม่อนุมัติเอง
> 4. Generate Config ทำใน transaction เดียวและล็อกแถว กันกรณี Admin ถอดถอนพอดีระหว่างสร้าง
> 5. Rate limit ทั่วไป 60 ครั้งต่อนาที ส่วน Login กับ Generate 10 ครั้งต่อนาที เกินแล้วได้ 429 พร้อม Retry-After
> 6. ถ้าแก้ของที่อนุมัติแล้วต้องรีวิวใหม่ และ Admin ถอดถอนฉุกเฉินได้พร้อมบันทึกเหตุผลครับ

## หน้า 18 ผลตรวจตามรายการเตรียมนำเสนอ (60 วินาที, ต่อด้วยเดโมสด)

> หน้านี้ตอบรายการตรวจของวิชาครับ
>
> ข้อแรก ฐานข้อมูลอยู่บน Supabase และมีข้อมูลจริงแล้ว มี MCP Server ที่อนุมัติแล้ว 39 ตัว Tool 458 ตัว และ Skill ที่อนุมัติแล้ว 138 ตัว
>
> ข้อสอง เอกสาร API อยู่ที่ docs/API.md ครบ 31 endpoint และ Postman 55 request รันผ่าน newman ได้ 81 assertion ไม่มีล้ม
>
> ข้อสาม ไม่มี token ได้ 401 role ไม่พอหรือไม่ใช่เจ้าของได้ 403 อยู่ในชุดเทสต์ 197 ข้อ ผ่านทั้งหมด
>
> ต่อจากนี้ผมขอเดโมสดเลยนะครับ

หมายเหตุ: ตัวเลข 39 server และ 138 skill ตรวจบนเว็บจริงเมื่อ 17 พ.ย. 2569 ถ้าสไลด์ยังเขียน 144 / 135 ให้แก้ตามรายการด้านบน

**สลับไปเดโมสดบน `contextforge-seven.vercel.app`** ทำตาม `docs/DEMO.md` ข้อ 4-5: สมัคร, ส่ง Skill ที่สแกนเจอ, Admin ปฏิเสธ, แก้แล้วอนุมัติ, ค้นหา, Generate Config, ลบได้ 204, Takedown เสร็จแล้วกลับมาที่หน้า 19

## หน้า 19 งานที่ยังไม่ทำ (50 วินาที)

> ส่วนที่ยังไม่ได้ทำมี 3 เรื่องครับ
>
> เรื่องแรก Row Level Security ของ Postgres ตอนนี้คุมสิทธิ์ที่ชั้น API อย่างเดียว ยังไม่มี policy ที่ฐานข้อมูล
>
> เรื่องที่สอง MFA สำหรับ Admin และตาราง audit log แยก ตอนนี้ใช้ submission_reviews บันทึกแทน
>
> เรื่องที่สาม endpoint จัดอันดับ เช่น Top Skill หรือกรองตามระดับความเสี่ยง
>
> อีกเรื่องที่ต้องบอกตรงๆ คือการสแกนเป็นการหาคำสำคัญ ไม่ได้วิเคราะห์โค้ด จึงรับรองไม่ได้ว่าปลอดภัยทุกกรณี Admin ยังต้องอ่านเองอยู่ครับ

## หน้า 20 ขอบคุณ (15 วินาที)

> ระบบเปิดใช้ได้ที่ contextforge-seven.vercel.app ครับ ขอบคุณอาจารย์ครับ มีคำถามเชิญได้เลยครับ

## คำถามที่อาจารย์น่าจะถาม

| คำถาม | ตอบสั้นๆ |
|---|---|
| ทำไมไม่ใช้ MongoDB | ข้อมูลผูกกันด้วย FK หลายชั้น PostgreSQL ได้ทั้ง JSONB และ FK ในตัวเดียว |
| เก็บ token ที่ไหน ทำไม | HttpOnly cookie, JavaScript อ่านไม่ได้ ลดความเสี่ยงจาก XSS |
| กันคนแก้ของคนอื่นยังไง | service เช็ก submitted_by เทียบกับ user ใน token ไม่ตรงได้ 403 |
| ลบแล้ว Config เก่าพังไหม | ไม่พัง ใช้ soft delete แถวยังอยู่ แค่ไม่แสดงในรายการ |
| 401 กับ 403 ต่างกันยังไง | 401 คือไม่รู้ว่าเป็นใคร (ไม่มีหรือ token ผิด), 403 คือรู้แล้วแต่ไม่มีสิทธิ์ |
| สแกน Prompt Injection เชื่อได้แค่ไหน | เป็นการหาคำสำคัญ ช่วยคัดกรอง แต่ Admin ยังต้องตรวจเอง |
| ถ้า Admin ลด role ใคร token เดิมยังใช้ได้ไหม | ยังใช้ได้จนกว่า token หมดอายุ เพราะ role อ่านจาก JWT แก้ได้โดยให้ token อายุสั้นลง หรืออ่าน role จาก DB ทุก request |
| ทำไม Generate ไม่ต้อง Login | ใช้ได้เฉพาะ Tool ที่อนุมัติแล้ว และมี rate limit 10 ครั้งต่อนาที Login แค่เพิ่มการบันทึกประวัติ |
